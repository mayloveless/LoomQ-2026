# LoomQ Optimization Backlog

> 这是一份阶段性优化候选清单，不属于当前主线任务。
>
> 当前原则：先完成赛题客观能力与正式提交要求，保持已稳定的 L1/L2 主路径不做无必要重构；主线完成后再集中评估这些候选项。

## 使用方式

- 只记录可验证、可落地、且与当前能力边界相关的优化点。
- 不因为出现新的想法就立即修改稳定代码。
- 待 L2/L3/提交链路完成后，统一做一次优先级评估，再拆成正式 task。
- 每项最终只做三种决策：`吸收` / `调整后吸收` / `不做`。

## 当前优化候选

### Agent 正确性

- [ ] **生成后做语义自验**：Parser/白名单校验只能证明 QASM 合法，不能证明实验目标正确。可考虑实际运行模拟器，将结果分布与用户目标进行比较，不通过时再触发修复。
- [ ] **目标判定与代码生成解耦**：避免同一次模型调用同时“理解目标 + 生成电路 + 声明目标”，否则模型可能把目标理解错后仍自洽通过。可评估使用独立 Judge（只看用户原话）生成验收目标，再对生成电路做语义验证。
- [ ] **对“标签冲突”和“电路真的错了”分开处理**：当目标族标签与实际分布冲突时，不要直接拿错误标签去反向修坏正确电路；可基于用户原始请求 + 模拟器真实分布做一次定向裁决，异常时仍按保守失败处理。
- [ ] **后端选择尽量确定性**：模型负责提取自然语言约束，最终后端筛选由 `backend_capabilities.json` 等确定性数据完成，减少模型记忆/幻觉导致的错误。
- [ ] **约束提取要求可回指用户原文**：模型输出的后端约束可携带原文 evidence，本地代码只接受确实能在当前 prompt 中定位且语义支持该归一化值的约束，避免模型凭空补出“免费 / 真机 / 零排队”等条件。
- [ ] **已知目标族采用受控语义 Oracle**：对 Bell/GHZ 等能可靠定义的目标，除语法外检查量子位宽度、完整测量映射和理想态等价；对未知目标不要把同样强度的结论泛化出去。
- [ ] **明确无法精确验证的边界**：对于无法推导理想分布的任意目标，不伪装成已经语义验证；至少做结构校验，并在产品层说明验证覆盖范围。
- [ ] **L2 的确定性规则不能绕过强制模型调用**：即使本地规则已经能生成、修复或选后端，正式 `agent_chat` 每个评分 case 仍须至少完成一次有效的组委会模型调用；规则适合作为约束、校验和 fallback，不能提前 return 导致该 case 失去得分资格。

### Agent 会话与鲁棒性

- [ ] **评分入口与产品会话分离**：`agent_chat(prompt)` 保持无状态、符合自动评测；用户入口可以维护独立 session，支持“改成 5 比特”“换成真机”等连续修改。
- [ ] **为模型异常输出准备降级路径**：结构化响应缺字段、JSON 围栏、额外文字、错误任务分类等情况应能解析或安全失败，避免单轮异常导致整个体验崩溃。
- [ ] **给 L2 设置明确资源预算**：在 120 秒总时限内限制 prompt/response 大小、JSON 深度/条目数、QASM 候选数量、qubit/gate 数和本地验证耗时，并预留最终返回时间，避免异常模型输出拖死整个 case。
- [ ] **生成失败时提供真实反馈再修复**：修复 prompt 优先携带 Parser/Simulator 得到的具体问题，而不是笼统要求“再试一次”。
- [ ] **修复重试保留历史最优候选**：模型重试可能越改越差；若多轮都未完全通过，可按明确的语义验证指标保留历史最佳版本，并明确标注未完全验证，避免机械返回最后一版。
- [ ] **Agent 写操作采用“提案 → 验证 → 用户确认 → 应用”**：生成/修复 QASM、切换关键配置等修改先展示摘要或 diff，本地校验通过后等待用户确认；提案绑定 base revision，工作区已变化时拒绝应用过期建议。
- [ ] **确定性回退必须显式标注来源和边界**：外部模型不可用时，只允许有限、可证明的本地预置路径继续；界面和机器字段都要区分“未调用模型”“尝试模型但失败”“模型真实生成”，自由问答不能伪装成本地生成的 AI 回复。

### 验证与回归

- [ ] **评估增加轻量参考态矢模拟器**：用尽量少的依赖独立计算理想 statevector / distribution，可同时服务 L2 语义自验、门分解验证、离线回归，以及后续 Quantum DevTools 的逐门状态轨迹；不要让正确性验证完全依赖三方 SDK。
- [ ] **回归样例必须具备“暴露目标错误”的能力**：位序测试使用非对称状态，相位/受控相位测试选择对相位错误敏感的电路，避免 Bell/GHZ 这类回文分布或天然均匀分布让实现错误也通过。
- [ ] **关键验证尽量做差分或独立裁判**：同一实现既生成结果又生成期望值时存在共同错误风险；核心路径优先使用独立参考实现、手算固定样例或另一条执行链做交叉验证。
- [ ] **有闭式或解析答案时优先作为独立测试 Oracle**：对可直接推导理想分布/不变量的电路，用数学结果作为基准，减少“参考模拟器与生产模拟器共享同一个 bug”的共同错误风险。
- [ ] **增加 round-trip / metamorphic 语义测试**：对 `source QASM → transpile → target/native → 可重解析表示` 的路径，在可行时比较执行分布或态矢等语义不变量；这类测试比单纯字符串快照更能发现转译错误。
- [ ] **正式执行路径应真实覆盖目标适配层**：`run(..., target)` 不应只用同一个源电路模拟器计算结果再更换 backend 名称；目标 codegen / runner / 位序归一化应在正式路径中被实际执行，辅助交叉验证不能替代 contract 主路径。
- [ ] **正式评测路径不要静默跨后端降级**：某目标 SDK / runner 不可用时，开发体验可以显式提示并允许用户切换，但 contract 路径不应偷偷改跑另一个后端后仍以原目标 backend 名义返回成功；否则会掩盖真实平台适配缺口。
- [ ] **公开 evaluator 只当契约 smoke test**：公开 PASS 不能推导隐藏集覆盖率；提交前应按题面明确描述的隐藏维度额外构造测试，尤其是改写 prompt、非对称位序、相位敏感电路、L3 随机语法组合与边界值。

### 交互与引导

- [ ] **首页提供具体自然语言示例**：不要只放“请输入量子实验需求”。给 3–4 个可以直接点击/填入的真实请求，让零量子背景用户知道自己可以怎样表达。
- [ ] **围绕“用户下一步想做什么”组织操作**：避免把“生成 / 修复 / 后端选择”直接作为产品菜单。根据当前状态动态提供 Quick Actions，例如“单步看看”“直接运行”“为什么是这个结果”“让 Agent 修复”“换真机运行”。
- [ ] **用“目标—电路—证据”组织同一个实验上下文**：目标说明用户想验证什么，电路/QASM 说明系统实际做了什么，验证/运行结果说明证据是否支持目标；不要让用户从聊天、编辑器、运行页和弹窗里自行拼上下文。
- [ ] **引导跟随操作出现，而不是独立教程前置**：用户第一次生成/执行时按上下文展示一句解释或可选“为什么”，不要求先学完量子概念再使用。
- [ ] **结果必须可视化**：最终 counts/probability 至少用清晰的分布图展示，让用户能一眼看到主峰、零概率项和噪声，而不是只读 JSON/文本数字。
- [ ] **结果旁边明确写“结论边界”**：不仅解释看到了什么，也说明当前测量不能证明什么，例如单一 Z 基测量只能展示相关性，不能单独认证纠缠，避免为了教学效果夸大科学结论。
- [ ] **运行结果采用不可变快照**：一次运行完成后保存当时的 QASM/revision/backend/shots/结果；后续编辑电路不能悄悄改写旧结果的语义，必要时提示“结果来自旧版本”。
- [ ] **无障碍能力按可测试契约设计**：关键状态不只靠颜色，图表有等价表格/文本，支持键盘焦点、`prefers-reduced-motion`、高缩放和色觉辅助；至少做多视口/缩放的自动浏览器检查，再补人工键盘和读屏验收。
- [ ] **真机等待过程要有可观察进度**：提交真机后及时展示已选平台、任务编号、当前等待/执行状态；超时或真机不可用时允许安全回落模拟器，不让用户面对长时间无输出。
- [ ] **真机结果与理想结果并列解释**：结构性结论以无噪声模拟器的理想分布为基准，真机数据用于解释噪声、泄漏和峰值偏差，避免直接从带噪分布猜“电路本来想做什么”。

### 产品差异化：Quantum DevTools

- [ ] **保留 DevTools 作为核心交互隐喻，但弱化“只给 Web 开发者”标签**：目标用户可描述为“没有量子背景的软件开发者 / AI 编程用户”。
- [ ] **QASM ↔ Circuit 双向定位**：代码行与量子门同步高亮，让 Agent 生成的代码具备可审查性。
- [ ] **按需查看目标平台原生表示**：在默认界面保持简单的前提下，可提供类似“compiled/native”视图查看 QASM 被转译后的目标代码，帮助开发者理解中间层实际做了什么。
- [ ] **模拟器单步执行**：提供 reset / previous / next / run-to-end；明确说明中间状态来自理想模拟器，不是假装真实 QPU 可以随意打断点读取状态。
- [ ] **展示执行前后状态 Diff**：优先验证概率分布、非零基态、振幅/相位等哪些信息真正对开发者有帮助，再根据人工使用反馈精简。
- [ ] **Agent 修复后可比较 Diff / 执行轨迹**：不仅告诉用户“修好了”，还让用户看到哪一行、哪一步导致结果变化。

### 真机证据与提交收尾

- [ ] **原始平台返回与归一化结果分开留存**：真机原始 payload 不修改，另生成符合统一 Schema 的归一化结果；文档明确位序、shots 补偿等转换规则，并尽量提供可复算脚本。
- [ ] **真机平台计分口径提交前单独核对**：区分“同一云平台上的不同设备”与“不同平台/provider”，不要仅凭设备数量推断可获得多个平台的真机加分。
- [ ] **提交前做一次官方契约漂移检查**：重新对照最新上游的 submission path、required files、`submission.yaml`、Docker/runtime 与 `prepare_submission.py`，不要仅依赖开赛早期 fork 的目录和配置；最终必须以当前官方预检通过为准。
- [ ] **运行时版本必须与全部后端 SDK 实测兼容**：Python / 基础镜像升级要视为契约变更，逐个验证 SpinQit、pyQPanda、Braket 的安装和执行；若依赖冲突则优先隔离 worker/venv，并在最终 Docker 中复测，不能只验证本地某一个环境。
- [ ] **增加“正式归档隔离”验收**：把最终 `starter_kit/` 单独复制到临时目录/镜像，仅依赖归档内文件重跑 evaluator、单测、L3/Bonus E2E 和 Web 启动，防止本地仓库根目录中的脚本或测试让提交看似可复现。
- [ ] **代码冻结后再生成可复现证据**：先形成干净 source snapshot，基于该 SHA 生成测试日志/manifest/哈希，再只提交 evidence；明确区分源码提交与证据提交，避免 manifest 自引用最终 commit 的不可能循环，也便于证明证据之后没有可执行代码变化。

### L3 / Bonus 若进入

- [ ] **L3 用随机程序 + 穷举测量值做差分测试**：参考解释器计算经典块期望终态，再与生成的 RISC-V 在官方模拟器上的执行结果逐项比对；同时保留少量手算固定样例降低共同错误风险。
- [ ] **L3 按完整迷你文法逐项做覆盖清单**：不能只覆盖公开样例形态；至少单测寄存器自引用/寄存器参与表达式（如 `r1 = r1 + 5`）、顺序赋值、嵌套 `if/else`、`==/!=`、多个测量位，并确认整数字面量的负数等边界是否可能进入随机生成器。
- [ ] **自定义量子 RISC-V 不只停在助记符**：若做 Bonus，优先把 opcode/字段编码、编解码实现和端到端语义测试三件事对齐，并用非对称电路验证 qubit 索引与字段映射。
- [ ] **参数门若进入自定义 ISA，要明确数值编码契约**：定义角度参数的位宽、范围、精度/定点格式、越界行为，并加入 `encode → decode` 往返误差测试和旋转门语义测试；若不支持参数门则明确写出范围边界与理由。

## 暂不执行

以上条目目前全部视为主线完成后的候选优化，不应打断：

1. L2 客观能力完成与稳定性验证；
2. L3 / Bonus 的取舍与实现；
3. Docker / submission / evidence 等正式提交闭环。

后续发现新的有效优化点，只追加真正有价值且不重复的条目。
